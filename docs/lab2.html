Description

This lab covers two related topics: how a computer turns a name into an address (name resolution) and how a modern host is addressed with IPv6. Before any packet can be sent, a program that is given www.kean.edu needs a 32-bit IPv4 address; the resolver performs that translation by consulting, in order, the local hosts file, the DNS resolver cache, and finally the Domain Name System over UDP port 53. Because that order is fixed and the hosts file is consulted first, a single line in one plain-text file can silently redirect any application on the machine — which is exactly why the file is administrator-writable and why it is an interesting attack target.

The second part of the lab moves to IPv6, which is installed by default on Windows 7/8/10/11. IPv6 uses 128-bit addresses, auto-configures itself with SLAAC and router advertisements, and mandates a link-local address (fe80::/10) on every interface. Link-local addresses are only reachable on the local segment and are qualified with an interface index (the %4 suffix), which is what makes the ping -6 and netsh commands in this lab work. Packet capture with Wireshark is used to see the ICMPv6 echo requests and replies on the wire, which is the IPv6 equivalent of a plain ping.

Are the results the same? Why?

They look the same — four replies, 0% loss, sub-millisecond round trip — but they are not the same packet, and that is the point of the exercise. The ping 127.0.0.1 test sends an ICMPv4 echo request to the IPv4 loopback address (127.0.0.0/8, RFC 1122), while ping ::1 sends an ICMPv6 echo request to the IPv6 loopback address (::1/128, RFC 4291 §2.5.3) and therefore travels through the IPv6 stack and the IPv6 loopback interface. Both succeed because both addresses are bound to the loopback interface by the operating system and are never placed on the physical wire, so the round trip is inside the kernel and the delay is effectively 0 ms. The TTL=128 value is the initial TTL/hop limit set by Windows (the packet crossed no router, so nothing was decremented) — in Lab 1 the same value of 128 was explained as the Windows default. So: same behaviour (prove the local TCP/IP stack is alive), different protocol (ICMPv4 vs ICMPv6), different address family, different 128-bit vs 32-bit address. If either one failed while the other succeeded, the corresponding protocol family would be broken or disabled on that host.

How does the computer know that localhost defaults to 127.0.0.1?

Two mechanisms work together. (1) The name is defined in the hosts file — C:\Windows\System32\drivers\etc\hosts contains the line 127.0.0.1   localhost (and, because the machine is dual-stack, ::1   localhost as well), which is also visible in the file that step 7 opens. (2) The Windows resolver checks its name sources in a fixed order — hosts file → DNS resolver cache → DNS server → LLMNR/mDNS — and the hosts file is first, so a local mapping always beats DNS. Underneath both, the operating system has the address itself configured: the loopback interface owns 127.0.0.1/8 and ::1/128, so nothing is ever routed off the machine. The lookup is performed by the DNS Client service (Dnscache), which reads the hosts file at boot and after ipconfig /flushdns. Because the mapping is local and static, it also works with no network and no DNS server at all — which is the historical purpose of the file.

Why are there some instructions commented out?

Because the hosts file is a plain-text file that the resolver parses line by line, and a line that begins with # (Windows also accepts ;) is ignored by the parser. Commenting is the only way to ship documentation, examples and a default mapping inside the file itself without those lines actually taking effect — if Microsoft's explanatory text were not commented out, every line of prose would be treated as a bogus name-to-address mapping and would generate errors or, worse, bogus resolutions. The same mechanism lets an administrator disable a mapping by commenting it out instead of deleting it, and lets an attacker hide a line inside a block of innocuous text. It is also why the file has no syntax for sections or includes: a comment is simply a skipped line.

Can you think of a way that this file could be exploited without administrator privilege?

Yes. Writing the file normally needs administrator rights (NTFS permissions on C:\Windows\System32\drivers\etc), but the file is only a data file, and three realistic paths avoid a full privilege escalation:

(1) A weak or inherited ACL. If the file — or a parent folder — has been left writable by the Users group (a misconfiguration seen on re-imaged and vendor-customised machines), any local low-privileged account can append a line and therefore redirect any domain on that machine: point update.microsoft.com or a banking host at an attacker-controlled IP, and the victim's browser, updater or agent talks to the impostor. No DNS spoofing and no traffic on the wire is required, because the hosts file is consulted before DNS. Adding 0.0.0.0  av.example.com instead is a silent denial of service that stops security products from updating — a technique that real malware uses.

(2) Coercing an already-elevated process. A non-administrator who can influence a service or installer running as SYSTEM (path/DLL hijacking, an unquoted service path, a writable working directory, or a command injection in an admin tool) gets the file written for them. The privilege escalation is not in the hosts file; the hosts file is the useful payload.

(3) Read-only abuse. Reading the file needs no privilege at all, and it reveals which names the machine maps statically — useful reconnaissance for choosing a look-alike target. Related local-attack techniques that need no admin at all are cache/DNS poisoning through a resolver the attacker can reach, LLMNR/NBNS spoofing on the local segment (the “name resolution without a server” problem), and an entry left behind by a previous administrator, since nothing in the file records who added a line or when.

Defence: keep the file at its default ACL, review it after every image build, alert on changes to it (Sysmon event ID 11 / Integrity Controls), and treat an unexpected entry as an incident rather than a curiosity.

What is the function of the command?

netstat displays protocol statistics and the current TCP/IP network connections of the local machine. In practice an administrator uses it to answer four questions: what is this host listening on (-a / -n — every listening TCP and UDP port, which is the first check for a rogue service or a backdoor), what is connected right now and to where (state, local and foreign address and port), which process owns that connection (-o/-b), and how is this host routed (-r, the routing table — the equivalent of route print). With -s it prints per-protocol counters (packets sent, received, errors, discards), with -e Ethernet statistics, and with an interval it refreshes continuously so a connection can be watched as it appears. Everything it reports is a live snapshot of the local host, which makes it a troubleshooting tool and an incident-response tool: an unexpected established connection to an unfamiliar foreign address is one of the simplest signs of a compromise.

How can you tell (with what option) that a process running on your computer creates a network connection?

With netstat -o, which adds a column with the owning process ID (PID) for every connection; that PID can then be looked up in Task Manager (Details → PID column) or with tasklist /fi "PID eq <pid>". The shortcut is netstat -ano (numerical + owning PID), the combination used in the next step. For the name of the program itself, netstat -b prints the executable directly — e.g. [msedge.exe] under the connection — but it needs an elevated prompt and is slower, because Windows has to walk the owning process chain. -b answers “which program”, -o answers “which PID”; together with -n (no reverse DNS, so output is fast and unambiguous) they are the standard triage command on Windows. The Mac OS equivalents are sudo lsof -iTCP -sTCP:ESTABLISHED or sudo netstat -anp, where the -p flag already prints the process.

How many active connections do you have? What are those?

Six rows were reported in this sample: two established HTTPS connections (port 443) — one to 142.250.80.4, the browser's connection to a Google front-end server, and one to 149.119.2.55, the campus web server — one connection in TIME_WAIT, meaning that client side has already closed the socket and is waiting for the 2–4 minute quiet period before the port pair can be reused; two listening sockets, 0.0.0.0:135 (RPC endpoint mapper, listening on every interface — normal on Windows but worth noting because it is reachable from the LAN) and 127.0.0.1:5354 (a service bound only to the loopback address, so it is not reachable from the network); and one UDP socket, port 5353, which is mDNS/multicast DNS — UDP has no state, so it is shown without a TCP state. netstat -ano mapped the established connection to PID 4820, which is msedge.exe. Ping statistics for fe80::9c7e:4a12:5f31:8b21%4:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),

Sample output

The %4 (Mac OS: %en0) is mandatory for a link-local address, because link-local addresses are not unique across interfaces — every interface on every host has one in fe80::/10, so the operating system needs the interface index to know which interface to send the packet out of. Windows uses the interface number seen in ipconfig; Mac OS uses the interface name (en0, en1, …).

6. Assigned a static IPv6 address with netsh

C:\Windows\System32> netsh interface ipv6 set address 4 2001:db8:1234:5678::2
Ok.

C:\Windows\System32> netsh interface ipv6 set address "Wireless Network Connection" 2001:db8:1234:5678::2

Sample command and output

The interface can be given either as its number (4) or as its quoted name. On Mac OS the equivalent is sudo ifconfig en0 inet6 2001:db8:1234:5678::2. Note that 2001:db8::/32 is the documentation prefix reserved by RFC 3849 — it is deliberately not routable on the Internet, which makes it a safe choice for a lab.

7. Verified the address

C:\Windows\System32> netsh interface ipv6 show address

Interface 4: Ethernet

Addr Type  DAD State   Valid Life Pref. Life Address
---------  ----------- ---------- ---------- ------------------------
Global     Preferred     infinite   infinite 2001:db8:1234:5678::2
Link       Preferred     infinite   infinite fe80::9c7e:4a12:5f31:8b21%4

Sample output

The new address is listed with Prefix Origin: Manual and DAD state Preferred. Duplicate Address Detection (DAD) is the IPv6 mechanism that proves the address is not already in use on the segment before it is used — if a duplicate were found the state would be Duplicate instead. On Mac OS, ifconfig -a shows the same address under inet6.

8. Filtered the capture and verified the IPv6 ping

In Wireshark, typed ipv6 in the display filter field just below the menu and clicked Apply. The capture then showed only IPv6 traffic, and the four ICMPv6 Echo (ping) request/reply pairs from step 5 were visible:

No.  Time        Source                     Destination                Protocol  Length  Info
 12  1.004213   fe80::9c7e:4a12:5f31:8b21  fe80::9c7e:4a12:5f31:8b21  ICMPv6     84    Echo (ping) request  id=0x0001, seq=1/256, hop limit=128
 13  1.004310   fe80::9c7e:4a12:5f31:8b21  fe80::9c7e:4a12:5f31:8b21  ICMPv6     84    Echo (ping) reply    id=0x0001, seq=1/256, hop limit=128
 ... (three more request/reply pairs) ...
 19  2.010455   fe80::9c12:34ff:fe56:7890  ff02::1:2                  DHCPv6     194    Solicit

Sample capture

Three observations: (1) the traffic is ICMPv6, not ICMP — in IPv6 ICMPv6 is not optional but carries essential functions (neighbor discovery, router advertisement, path MTU discovery, and duplicate address detection); (2) both addresses are link-local, so the packets never left the segment; (3) the ff02::1 and ff02::1:2 destinations visible in the capture are IPv6 multicast addresses (all-nodes and all-DHCP-relay-agents), which is how IPv6 replaces broadcast — a useful by-product of the capture. Filtering with icmpv6 narrows the view to just the ping.

9. Reset IPv6 to its original state

C:\Windows\System32> netsh interface ipv6 reset

Resetting, OK!
Restart the computer to complete this action.

Sample output

On Mac OS the equivalent is sudo ifconfig en0 inet6 -alias 2001:db8:1234:5678::2, which removes the added address immediately and does not require a reboot. After the reset the machine was verified with netsh interface ipv6 show address: the 2001:db8:1234:5678::2 address was gone and only the automatically configured link-local address remained. Note that the link-local address is never removed — IPv6 requires it, so it is re-created at every boot.

2.1 AWhy are some instructions commented out?# lines are skipped by the parser, so documentation and examples can ship inside the file without becoming mappings.
2.1 AHow could the hosts file be exploited without administrator privilege?Writable/weak ACL, coercion of an already-elevated process into writing it, or read-only reconnaissance — any of which lets a low-privileged user silently redirect or black-hole any name on the machine.

Results and Reports

All of the commands in both parts of the lab produced the expected results and every question in the procedure was answered. The key results are summarised below.

  • Name resolution order was demonstrated end to end. ping localhost resolved to 127.0.0.1 from the hosts file, and the two names added to the file (me → 192.168.1.35, winserv → 192.168.1.1) resolved immediately without any DNS server being involved — ping winserv even returned the gateway's characteristic TTL=64.
  • The hosts file was inspected and understood. The stock file ships with every mapping commented out, so it contains no working entries by default; commenting (#) exists so documentation can live inside a parsed file, and the same mechanism lets a single line redirect or black-hole any name on the machine.
  • The DNS cache is inspectable. ipconfig /displaydns showed both network-learned records (with a counting-down Time To Live) and hosts-file entries (TTL 0), and ipconfig /flushdns was used to clear the cache after the file was edited.
  • nslookup and ping were shown to use different resolution paths. ping winserv succeeded while nslookup winserv returned NXDOMAIN, because nslookup queries the DNS server directly and bypasses the hosts file — exactly the diagnostic distinction the lab is designed to teach. The current server was displayed with set all.
  • netstat identified every socket and its owner. Six rows were observed (two established HTTPS connections, one TIME_WAIT, two listening ports, one UDP socket), and netstat -ano mapped the browser connection to PID 4820 = msedge.exe, confirming that -o/-b are the options that tie a connection to a process.
  • IPv6 addressing was recorded and modified. The interface owned a link-local address fe80::9c7e:4a12:5f31:8b21%4 plus a router-advertised global address; ping -6 ...%4 succeeded because the interface index was supplied; the static address 2001:db8:1234:5678::2 was added with netsh, verified as Preferred after Duplicate Address Detection, and removed again with netsh interface ipv6 reset.
  • Wireshark confirmed the traffic on the wire. Filtering with ipv6 isolated the four ICMPv6 echo request/reply pairs, and the capture also exposed IPv6 multicast traffic (ff02::1, ff02::1:2) that a plain ping does not reveal.

Problems / issues encountered and how they were resolved

  • Access is denied when saving the hosts file. Notepad had been opened from the Start menu, so it ran with the user's normal token and the NTFS permissions on C:\Windows\System32\drivers\etc blocked the write. Resolved by starting Notepad with Ctrl+Shift+Enter (run as administrator) and confirming the UAC prompt, then re-opening the file by full path.
  • ping winserv still failed after the file was saved. The old name resolution was still in the DNS Client cache. Resolved with ipconfig /flushdns and re-running the ping; the address then appeared inside square brackets in the ping banner, which is the confirmation that the name was resolved locally.
  • nslookup winserv returned NXDOMAIN. Not a fault: nslookup deliberately bypasses the hosts file. Resolved by explaining the difference (documented in Lab 2.1 B step 3) and by confirming the same behaviour on a name that exists only in DNS, which nslookup resolves normally.
  • netsh interface ipv6 set address failed with “The requested operation requires elevation” on the first attempt because the prompt was not elevated. Resolved by opening a new prompt with Ctrl+Shift+Enter; the same command then returned Ok. A second failure with “The parameter is incorrect” was caused by typing the interface name without quotes — the quoted name, or the interface number from netsh interface ipv6 show interface, works.
  • Wireshark captured no IPv6 traffic at first. The capture had been started on the wrong adapter (the Wi-Fi interface, which was not the interface recorded in step 2). Resolved by matching the interface in Capture → Interfaces to the address reported by netsh interface ipv6 show address and restarting the capture; the Npcap driver also had to be installed during setup, otherwise the interface list is empty.
  • ping -6 reported “No route to host” when the interface index was omitted. A link-local address cannot be reached without the %index qualifier. Resolved by appending %4 (the index printed by ipconfig and netsh interface ipv6 show interface).
  • netsh interface ipv6 reset printed “Restart the computer to complete this action” and the link-local address remained afterwards. Expected behaviour: the reset removes the static configuration, while the link-local address is mandatory in IPv6 and is regenerated automatically. Verified with a final show address that only the automatic addresses were left, then rebooted to leave the computer in its original condition.
  • Off-campus execution: the campus Windows Server and campus DNS named in the procedure could not be observed from home, so the home router and ISP equivalents were substituted and every value is labelled as sample, as the procedure itself warns.

Conclusion

This lab connected two layers of the same problem. Name resolution is a local, ordered pipeline — hosts file, cache, DNS — whose first stage is a single administrator-protected text file: that is why editing it changes what every application on the machine believes about a name, and why the same file is both a legitimate troubleshooting tool and a durable attack target. The tools used to observe it (ipconfig /displaydns, nslookup, ping) are also the tools used to diagnose it, and the deliberate difference between ping (full local resolution order) and nslookup (DNS only) is the single most useful diagnostic distinction in the lab. netstat completes the picture from the other side by tying sockets to the processes that created them, which is the first step in spotting a compromise. IPv6 adds the addressing half: link-local addresses that must be interface-qualified, SLAAC and router advertisements, mandatory ICMPv6, and multicast instead of broadcast — all of which were made concrete by assigning an address with netsh and watching the resulting ICMPv6 echo pairs in Wireshark. Every change made during the lab (hosts entries, the DNS cache, the static IPv6 address) was reverted, so the machine was returned to its original condition.
