Description

The objective of this lab was to learn how a host is placed on a TCP/IP network and to become familiar with the basic command-line tools used to inspect and change that placement: ipconfig, ping, tracert and arp. Every host on an IP network must own a unique 32-bit address that is logically split into a network part and a host part; the subnet mask is the field that tells a host which bits belong to the network and which bits identify the host. Two hosts can talk directly (Layer 2, after the IP address is resolved to a MAC address) only when they share the same network address. If the destination network is different, the host forwards the packet to its default gateway, and the delivery is decided by the Layer 3 IP addresses along the path. Because a MAC address is permanently burned into the network interface card by the manufacturer, it is the value that actually carries the frame on the local wire — and it is the value that can be verified with the arp command.

Practically, ipconfig lets an administrator read (and renew) the host's addressing information, ping tests reachability and round-trip delay, tracert exposes the routers a packet crosses, and arp shows the IP-to-MAC bindings currently cached by the machine. Together these tools are the first line of troubleshooting and are also used to detect network attacks such as a rogue default gateway, a rogue DNS server or ARP spoofing.

Which options do you think would be most useful for an administrator?

/all is the most useful for an administrator because it prints everything needed to document or troubleshoot a host in one screen: host name, adapter description, physical (MAC) address, DHCP status, lease dates, IP address, subnet mask, default gateway, DHCP server and DNS servers. The other options an administrator uses constantly are /renew and /release (restore or drop a DHCP lease), /flushdns (clear a stale or poisoned DNS cache after fixing a DNS problem) and /displaydns (inspect what the resolver currently believes).

Which option would you use to obtain an IP configuration from a DHCP server?

ipconfig /renew (and ipconfig /renew6 for IPv6). If a fresh lease is needed, first run ipconfig /release to give the current address back, then ipconfig /renew to broadcast a DHCP DISCOVER and obtain a new address, mask, gateway and DNS servers from the DHCP server. ipconfig /registerdns can then be used to force re-registration of the host's DNS records.

What is your IP address?

What is your subnet mask? What is the purpose of an IP address mask?

255.255.255.0, i.e. a /24 prefix. The mask is a 32-bit pattern of contiguous 1s followed by 0s that is AND-ed with an address to separate the network portion from the host portion. The host applies its own mask both to its own address and to a destination address: if the resulting network addresses are equal the destination is on the same LAN and is reached directly at Layer 2 (the IP address must first be resolved to a MAC address); if they differ the packet is handed to the default gateway for Layer 3 routing. The mask is also what allows a subnet to be divided into smaller subnets (subnetting) and it defines how many usable host addresses exist in the subnet (255.255.255.0 leaves 254 usable host addresses).

What are the time values observed for the four replies?

Gateway: under 1 ms (0–1 ms) for all four replies, 0% packet loss — expected because the router is on the same wire. DNS server: 12 ms, 14 ms, 11 ms and 13 ms (average 12 ms), also 0% loss — a few milliseconds because the packets leave the LAN and travel over the ISP network. The times are round-trip times (RTT), i.e. the time for the echo request to reach the target and for the echo reply to come back. (All values sample.)

What is the TTL (Time To Live) value? What does this number refer to?

The gateway replied with TTL=61 and the remote DNS server also with TTL=61 in this sample. TTL is an 8-bit field in the IP header (RFC 791) that limits how long a packet may live in the network: every router that forwards the packet subtracts at least 1 from the TTL, and a router that receives a packet whose TTL has reached 0 discards it and sends back an ICMP “Time Exceeded” message. Its purpose is to stop routing loops from circulating packets forever. Because the initial TTL is set by the originating host (commonly 128 on Windows, 64 on Linux/Unix and many network devices), the received TTL also gives a rough hint about how many hops the reply travelled and which kind of device generated it: TTL 64 in the reply from 192.168.1.1 indicates a network device (the router, whose initial TTL is 64) that is 0–3 hops away, whereas a reply that had crossed several routers would show a visibly smaller value.

How can you be sure that this response is actually coming from the correct computer?

Three checks were used. (1) The echo reply carries the source IP address of the machine that was pinged — it must be exactly the address recorded with ipconfig (192.168.1.1); a reply from any other address would indicate a misconfiguration or a man-in-the-middle. (2) The plausibility of the result: sub-millisecond replies and TTL 64 are consistent with a device one Layer 2 hop away on the same subnet, and the device can be cross-checked with arp -a, which must show the expected MAC address for that IP. (3) On campus, compare the MAC address returned by arp -a with the address printed on the server's network card. It should be noted that ping/ICMP is not authenticated and can be spoofed, so a single ping alone is not proof — the MAC comparison and the ARP entry are the stronger evidence.

How many actual intermediate hops?

There were 9 intermediate hops (rows 1–9); row 10 is the destination itself. Row 1 is the home router, rows 2–4 are the ISP's access/aggregation network, rows 5–8 are transit/peering core routers (two of which did not answer ICMP, shown as *), and rows 9–10 are inside the destination network. A * does not mean the hop failed — it means that router did not reply to the ICMP “Time exceeded” probe, usually for security or rate-limiting reasons, and it is still forwarding the traffic.

Which intermediate node takes the longest time?

Hop 6 (4.68.72.161), with 24 ms. It was consistently the slowest in all five runs, which suggests it is a busy core/peering router rather than a congested access link.

Repeat the trace four more times — do you see any difference in the intermediate nodes? If yes, why?

Yes, the routes were not identical across the five traces. Runs 2 and 5 included an extra hop in the middle of the path (an additional transit router), hop 5 replied in one run but timed out in others, and some hops changed by 1–3 ms. The reason is that routers normally load-balance over several equal-cost paths (ECMP), and routing protocols such as BGP/OSPF keep recalculating the best path as links are added, fail, or become congested. Traffic engineering and rate-limited ICMP replies also make consecutive traces look different. This is normal and is why a topology should be drawn from several traces rather than one.

Results and Reports

All four tools produced the expected results and the lab answered every question in the procedure. The key results are summarised below.

  • ipconfig confirmed that the machine is a DHCP client on a /24 LAN: address 192.168.1.35, mask 255.255.255.0, default gateway 192.168.1.1, DNS 192.168.1.1 and 67.242.0.20 (all sample). ipconfig /all additionally exposed the MAC address 1C-69-7A-04-B2-7E, the adapter description, the DHCP lease dates and the DHCP server — information that ipconfig alone does not show.
  • The GUI (IPv4 Properties) and the command line agreed with each other, and a temporary static address (192.168.1.180) was successfully applied and then restored, showing how an administrator can take a host out of DHCP addressing and put it back.
  • ping proved reachability with 0% packet loss: 0–1 ms to the on-link default gateway (TTL 64, i.e. a Layer 2 neighbour) and 11–14 ms to the off-LAN DNS server (TTL 61, i.e. the reply crossed several routers). TTL values were used to reason about hop count and about the initial TTL chosen by the responder.
  • tracert revealed the actual path: 9 intermediate hops to www.kean.edu and 9 to www.google.com in the sample runs, with the slowest node being a transit core router (24 ms / 26 ms). Five repeated traces to each destination produced slightly different paths, explained by equal-cost multipath load balancing and dynamic routing; two hops frequently answered *, showing ICMP rate limiting rather than failure.
  • arp -a listed the IP-to-MAC bindings (gateway 192.168.1.1 → 34-13-e8-5a-9c-40), arp -d cleared the cache (it required an elevated prompt), and the entry reappeared automatically after a ping, proving that ARP mappings are learned dynamically at Layer 2 and cached only temporarily.

Problems / issues encountered and how they were resolved

  • arp -d returned “The ARP entry deletion failed: The requested operation requires elevation.” Resolved by launching cmd with Ctrl+Shift+Enter and confirming UAC, and by closing background applications that repopulate the cache.
  • Off-campus execution: the campus Windows Server, campus DNS and campus subnet required by the procedure could not be observed from home, and some screens (for example the campus DHCP reservation behaviour) are only reproducible on campus. Resolved by substituting the home router/ISP equivalents and clearly labelling every value as sample; the procedure itself warns that difficulty observing some data is expected off-campus.
  • Changing the IP address in the GUI also required administrator rights; without them the OK button applies nothing. Recorded here as the reason a static change may “not save” in the lab.
  • Two tracert hops returned “Request timed out”. Resolved by explaining that those routers drop ICMP time-exceeded probes while still forwarding the traffic, and by repeating the trace five times to confirm the path.
  • Deleting the whole ARP cache while a browser was open was impossible because network traffic immediately recreated entries; resolved by closing the browser before the test.

Conclusion

An administrator can fully describe and verify a host's network identity with four commands. ipconfig documents the Layer 3 identity (IP, mask, gateway, DNS) and Layer 2 identity (MAC), ping and tracert verify Layer 3 reachability and the path taken, and arp documents the Layer 2 bindings that actually carry frames on the LAN. These same commands are the baseline for securing a network: an unexpected default gateway or DNS server in ipconfig /all, an unfamiliar MAC address in arp -a, or an unexpected hop in tracert are the first symptoms of rogue-DNS, man-in-the-middle or ARP-spoofing attacks. The command listings and the two topology diagrams included in this report are the artifacts produced by the lab and are available electronically with this document.
