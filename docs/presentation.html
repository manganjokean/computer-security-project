SECTION: PROBLEM

Slide 2 — Why IoT security is different (1:00)

Three constraints that rule out normal defenses:

  1. No endpoint agent possible — not enough storage, memory, or power
  2. Rarely patched — vendors abandon devices; users never update
  3. Physically exposed — same Wi-Fi as laptops; default credentials

Result: the only control that scales is network-side monitoring.

Visual: photo/collage of a doorbell camera, thermostat, baby monitor with "cannot install antivirus" crossed out.

Slide 3 — The threat + research question (1:00)

  • Mirai / BASHLITE lifecycle: propagate → infect → C&C → execute attacks
  • Mirai powered some of the largest DDoS attacks on record
  • We target the execution stage — the stage that causes external harm

Research question: Can behavioral network-traffic features accurately distinguish benign IoT traffic from botnet-infected IoT traffic?

SECTION: METHODOLOGY

Slide 5 — Preprocessing (1:00)

Flow diagram left → right:

Load → Deduplicate (−96 rows) → Stratified split (device × label, 120,166 / 30,042) → Variance/correlation pruning (115 → 36) → Median impute (0 missing) → One-hot encode → Standardize → Class weighting

Three "why" callouts (pick the ones you're asked about most):

  • Dedupe before split — flood generators emit identical rows (96 found, 0.06%); otherwise they leak into the test set
  • Correlation pruning — 334 feature pairs had |r| > 0.95; kept 36 of 115 to avoid redundant collinear inputs
  • Class weighting — 92% of training rows are malicious; accuracy would reward guessing the majority class

SECTION: CONCLUSION

Slide 12 — Closing (1:00)

Answer: Can abnormal IoT traffic be detected? → Yes — with caveats. XGBoost F1 = 1.0000 · ROC-AUC = 1.0000, and it holds across all nine devices (F1 = 1.0000 on eight, 0.9999 on the Ecobee thermostat).

Four takeaways:

  1. Network-side detection works for devices that can't protect themselves — no agent, no patch, no vendor cooperation
  2. Floods easy, scanning hard — and it's the anomaly detector that fails it (0.0000 on mirai_scan/mirai_syn)
  3. Signal is volume + socket burstiness at the 10 ms window, not malware content (14.5 → 3,689.6 packets/0.1 s)
  4. Accuracy is the wrong metric for security — FPR and FNR are what operators feel

Limitations (say at least two): lab vs. production traffic · inverted class prior (92% malicious) · only 2,416 benign test flows → true FPR only bounded to ≲0.124% · random rather than chronological split · no adversarial testing · two botnet families only.

Likely Q&A — and how to answer

Q: Your accuracy is ~99%. Isn't this a solved problem?

"On this benchmark, yes. But that's exactly why the rubric says accuracy isn't the goal. Three caveats: the corpus is 92% attack traffic — 11.4 malicious records per benign one — which is the inverse of production, so precision will collapse under a realistic prior; we split randomly rather than chronologically, so near-identical consecutive flow snapshots may straddle the split; and with only 2,416 benign test flows, a measured zero false-positive rate only bounds the true rate to about 0.124%. All three inflate the number."

Q: The Isolation Forest only got F1 = 0.39. Does that mean anomaly detection is useless?

"No — it means this configuration of it is. One pooled model, default contamination, no per-device baseline, no threshold tuning, no voting window. The original N-BaIoT paper reached 100% TPR with one deep autoencoder per device and thresholds optimised on held-out benign traffic. The gap is the security lesson: anomaly detection is extremely sensitive to per-device baselining, and a naively configured detector can be worse than useless. That's also why our per-device results show it collapsing to 0.0015 F1 on two devices while a pooled supervised model stays at 1.0000."

Q: Why four models instead of two?

"The rubric requires two. I used four because Isolation Forest answers a fundamentally different question — it's trained on benign data only and never sees an attack, which is the only realistic setting when a new botnet appears. Comparing it to supervised models quantifies what's lost without labels."

Q: Wouldn't this be defeated by an attacker who knows your features?

"Possibly — that's limitation #4. An attacker who rate-limits and pads jitter could blend in. We did no adversarial testing, and that's the honest limitation. It's also a strong argument for periodic re-baselining."

Q: Why not just put an agent on the device?

"That's the central constraint of IoT security: no storage, no compute budget, no vendor patches. Network-side monitoring is the only approach that scales and requires zero cooperation from the device."

Q: Is 150k rows enough?

"It's a proportional stratified sample of the full 7,062,606-row corpus, chosen so the notebook runs in minutes on a free Colab instance. Sampling is proportional across every device and all ten traffic types, and all seeds are fixed for reproducibility. What is not big enough is the benign class — 2,416 benign test flows is the real statistical weakness, not the total row count."

Q: What would you do differently?

"Chronological splitting to remove leakage, an adversarial robustness evaluation, and a streaming harness to measure detection latency — the original paper reports ~174ms, which is the number a real IDS needs."
